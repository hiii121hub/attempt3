# Capacity admission and teardown — October 13, 2026

This is admission/lifecycle engineering, **not five-active-user performance proof**.
Production still defaults to one supervised tester; development retains its existing
default. The unchanged `POXEY_MAX_SESSIONS=5` setting is the eventual validated
release target. The existing 25-minute allowance, retry policy, UI and routes remain.

## Implemented

The single broker reserves a synchronous capacity lease before starting resources.
A lease covers startup, the active session and teardown. Five occupied leases reject
a sixth with the existing HTTP 429 `MAX_SESSIONS` message; the other leases are
untouched. The existing serialized startup lock still returns
`SESSION_CREATION_BUSY` during a launch, which the existing bounded frontend retry
handles. `MAX_SESSIONS` is not retried by that helper. No new automatic retry of
ambiguous network failures was added.

A successful startup transfers its lease to the session. A failed startup releases
it after successful rollback. A failed rollback retains the lease (fail closed).
On normal end, expiry or process failure, stream authorization is removed immediately,
but the slot and display/port allocation remain reserved until cleanup completes.
SIGTERM is followed by SIGKILL if necessary; sending a signal no longer counts as
process exit. Profile deletion waits for the tracked child processes to exit.
The sink is unloaded, usage bookkeeping is retained, and shutdown waits for pending
normal cleanup rather than exiting before the profile-removal timer.

`GET /health` now includes `occupiedSlots`, alongside the existing `sessions` and
`maxSessions`: starting/retiring or failed-cleanup reservations can make occupied
slots larger than active sessions. This loopback diagnostic is not publicly proxied.
If cleanup/accounting fails, the reservation remains and a diagnostic is logged.
Do not manually reset capacity to bypass an error: reconcile owned resources and
the ledger before a scheduled restart. Durable crash recovery and container-wide
process verification remain required by the isolation design.

## Tests and limits

`npm run test:capacity` tests five-versus-six admission, 100 concurrent reservation
attempts, idempotent release, startup rollback, delayed teardown, invalid limits,
cleanup errors and a real TERM-resistant Node child with real profile deletion and
ledger/other-profile preservation. These are **not 100 Chrome launches**.
Security regression guards verify configuration defaults and manager wiring.

CPU/memory/PID limits are generated by the offline container specification only;
the native runtime does not suddenly acquire per-session cgroups. Do not enable
public multi-user use until a qualified Linux host enforces those limits, the
isolation acceptance tests pass and five real viewers pass sustained load testing.
